บทที่ 3

การวิเคราะห์และออกแบบระบบ (System Analysis and Design)

การพัฒนา ระบบจองคิวนวดแผนไทย ศูนย์สุขภาพชุมชนท่าวังหิน มีวัตถุประสงค์เพื่อสร้างนวัตกรรมระบบบริการสุขภาพทางไกลและบริหารจัดการการนัดหมายที่มีความสะดวก ปลอดภัย และมีประสิทธิภาพสูง ครอบคลุมทั้งแอปพลิเคชันสำหรับประชาชนผู้รับบริการ (Flutter Cross-Platform Application) และระบบแดชบอร์ดบริหารจัดการสำหรับเจ้าหน้าที่และแพทย์แผนไทย (Web Admin Dashboard) ผ่านการเชื่อมต่อกับระบบให้บริการข้อมูลส่วนกลาง (Node.js/Express RESTful API) และฐานข้อมูล Cloud Firestore

ในบทนี้จะนำเสนอรายละเอียดการวิเคราะห์และออกแบบระบบตามระเบียบวิธีวิศวกรรมซอฟต์แวร์ ประกอบด้วย การวิเคราะห์ความต้องการของระบบ (Requirement Analysis), แผนภาพกรณีการใช้งาน (Use Case Diagram) พร้อมตารางอธิบายรายละเอียดกรณีการใช้งาน (Use Case Descriptions), แผนภาพลำดับการทำงาน (Sequence Diagrams) พร้อมอธิบายหลักการทำงานอย่างละเอียด, แผนภาพความสัมพันธ์ของข้อมูล (Entity-Relationship Diagram: ER Diagram) และโครงสร้างฐานข้อมูล (Database Schema)

3.1 การวิเคราะห์ความต้องการของระบบ (Requirement Analysis)

จากการศึกษาและรวบรวมความต้องการของศูนย์สุขภาพชุมชนท่าวังหิน สามารถจำแนกความต้องการออกเป็น 2 ด้านหลัก ดังนี้:

3.1.1 ความต้องการเชิงฟังก์ชัน (Functional Requirements)

1. ส่วนของผู้ใช้บริการ (Customer / General User) ผ่านแอปพลิเคชัน Flutter:

  • ระบบยืนยันตัวตนดิจิทัล (Digital Authentication): รองรับการเข้าสู่ระบบผ่าน ThaiD Digital ID (DOPA OpenID Connect) ด้วยการตรวจจับลายเซ็นดิจิทัล (JWKS/PKCE) และรองรับการเข้าสู่ระบบด้วยหมายเลขโทรศัพท์ (Firebase Phone OTP)
  • ระบบจัดเก็บข้อมูลติดต่อสำรอง: บังคับให้ผู้ใช้งานที่เข้าสู่ระบบผ่าน ThaiD กรอกเบอร์โทรศัพท์ เพื่อให้เจ้าหน้าที่สามารถติดต่อได้ในกรณีฉุกเฉิน
  • ระบบสืบค้นบริการ (Services Catalog): แสดงรายการหัตถการนวดแผนไทย รายละเอียด ระยะเวลานวด และอัตราค่าบริการ
  • ระบบจองคิวนวดแผนไทย (Online Booking): สามารถเลือกวัน เวลา บริการ และระบุแพทย์แผนไทย/หมอนวดที่ต้องการได้ พร้อมระบบตรวจสอบเวลาว่างแบบ Real-time Transaction
  • ระบบติดตามคิวสด (Live Queue Tracking): แสดงหมายเลขคิวที่กำลังรับบริการ จำนวนคิวที่รอก่อนหน้า และเวลาคาดการณ์ในการรอ
  • ระบบจัดการประวัติการจอง: ตรวจสอบประวัติการจองย้อนหลัง และยกเลิกการจองได้ตามเงื่อนไขเวลาที่กำหนด
  • ระบบศูนย์การแจ้งเตือนและการยืนยันรับทราบ (Notification & Acknowledgement): รับการแจ้งเตือนเมื่อถึงคิว พร้อมปุ่ม "กดยืนยันรับทราบ" เพื่อส่งสัญญาณกลับไปยังเจ้าหน้าที่

2. ส่วนของเจ้าหน้าที่และผู้ดูแลระบบ (Admin / Staff) ผ่าน Web Admin Dashboard:

  • ระบบรักษาความปลอดภัย: เข้าสู่ระบบด้วย Email/Password พร้อมตรวจสอบสิทธิ์ Admin Custom Claims
  • แดชบอร์ดสรุปสถิติภาพรวม (Real-time Overview): แสดงตัวเลขคิววันนี้, คิวรอยืนยัน, คิวกำลังนวด, คิวเสร็จสิ้น และจำนวนหมอนวด
  • ระบบจัดการคิวงาน (Queue Management): มีปุ่มเรียกคิวถัดไป (Call Next) และปรับสถานะคิวงานได้ตามขั้นตอน
  • ระบบจัดการข้อมูลหมอนวด (Therapist Management): เพิ่ม ลบ แก้ไข ข้อมูลหมอนวด ประสบการณ์ และสถานะความพร้อม
  • ระบบติดตามการแจ้งเตือนลูกค้า: ตรวจสอบว่าลูกค้ารับทราบการเรียกคิวแล้วหรือไม่ หากยังไม่กดยืนยัน จะมีเบอร์โทรศัพท์ให้เจ้าหน้าที่โทรติดต่อได้ทันที
  • ระบบส่งออกข้อมูลไปยัง Google Sheets: ซิงค์ข้อมูลการจองทั้งหมดไปยัง Google Spreadsheet อัตโนมัติด้วยคลิกเดียว
  • ระบบส่งอีเมลแจ้งตารางงานหมอนวด: สรุปคิวงานประจำวันและส่งอีเมลแจ้งหมอนวดแต่ละท่านแยกรายบุคคลผ่าน SMTP

3.1.2 ความต้องการเชิงไม่เกี่ยวข้องกับฟังก์ชัน (Non-Functional Requirements)

  • ด้านความปลอดภัย (Security): ข้อมูลอัตลักษณ์ดิจิทัลผ่าน ThaiD รองรับมาตรฐาน OAuth 2.0 / OIDC ป้องกันการปลอมแปลง Token ด้วย JWKS Signature มีระบบป้องกัน API ด้วย helmet และ express-rate-limit
  • ด้านความถูกต้องและภาวะพร้อมกัน (Concurrency Control): ใช้ Firestore Transaction ควบคุมการจอง ป้องกันปัญหาการจองเวลาเดียวกันซ้ำซ้อน (Double Booking / Race Condition) 100%
  • ด้านความเข้ากันได้และการตอบสนอง (Cross-Platform Usability): แอปพลิเคชันฝั่งลูกค้ารองรับการทำงานทั้งบน iOS, Android และ Web Browser ส่วนแดชบอร์ดของเจ้าหน้าที่รองรับหน้าจอคอมพิวเตอร์และแท็บเล็ต

3.2 แผนภาพกรณีการใช้งาน (Use Case Diagram)

แผนภาพกรณีการใช้งาน (Use Case Diagram) แสดงความสัมพันธ์ระหว่างกลุ่มผู้ใช้งาน (Actors) ได้แก่ ผู้ใช้บริการ (Customer), ผู้ดูแลระบบ/เจ้าหน้าที่ (Admin/Staff) และระบบภายนอก (ThaiD, Google Sheets, Mail Server) กับฟังก์ชันหลักของระบบ ดังแสดงในภาพที่ 3.1

ภาพที่ 3.1 แผนภาพกรณีการใช้งาน (Use Case Diagram) ของระบบจองคิวนวดแผนไทย

3.3 รายละเอียดกรณีการใช้งาน (Use Case Descriptions)

ตารางอธิบายรายละเอียดกรณีการใช้งานระบุขั้นตอนการทำงาน เงื่อนไข และการจัดการข้อผิดพลาดในแต่ละฟังก์ชัน:

ตารางที่ 3.1 รายละเอียด Use Case: UC-01 การเข้าสู่ระบบและยืนยันตัวตน (Authentication)
รหัส Use CaseUC-01
ชื่อกรณีการใช้งานการเข้าสู่ระบบและยืนยันตัวตน (Authentication)
ผู้กระทำ (Actor)ผู้ใช้บริการ (Customer), ผู้ดูแลระบบ (Admin), ระบบ ThaiD DOPA
วัตถุประสงค์เพื่อระบุตัวตนและออก Token สิทธิ์การเข้าถึงระบบที่ปลอดภัย
เงื่อนไขก่อนทำ (Pre-condition)ผู้ใช้งานเปิดแอปพลิเคชัน Flutter หรือเปิดหน้า Web Admin Dashboard
เงื่อนไขหลังทำ (Post-condition)ระบบออก Authentication Token และนำผู้ใช้เข้าสู่หน้าจอตามสิทธิ์การใช้งาน
ขั้นตอนหลัก (Main Flow) 1. ผู้ใช้เลือกวิธีการเข้าสู่ระบบ (ThaiD Digital ID / Phone OTP / บัญชีผู้ดูแลระบบ)
2. กรณี ThaiD: ระบบนำไปยังหน้ายืนยันตัวตน ThaiD → ตรวจสอบ JWKS Signature → ออก Firebase Custom Token → นำผู้ใช้กลับเข้าสู่แอปพลิเคชัน
3. กรณี Phone OTP: ผู้ใช้กรอกเบอร์โทร → รับรหัส OTP 6 หลัก → กรอกยืนยัน
4. กรณี Admin: เจ้าหน้าที่กรอก Email และ Password → ตรวจสอบ Claim admin: true
5. ระบบบันทึกสถานะการล็อกอินและนำผู้ใช้เข้าสู่หน้าจอหลัก
ขั้นตอนสำรอง (Alt Flow) 2a. การยืนยันตัวตน ThaiD ไม่สำเร็จหรือถูกยกเลิก: ระบบแสดงแจ้งเตือนและกลับมาหน้าล็อกอินเดิม
4a. รหัสผ่านไม่ถูกต้อง หรือไม่มีสิทธิ์ Admin: ระบบแสดงข้อความปฏิเสธการเข้าถึง
ตารางที่ 3.2 รายละเอียด Use Case: UC-03 การจองคิวนวดแผนไทย (Booking & Slot Validation)
รหัส Use CaseUC-03
ชื่อกรณีการใช้งานการจองคิวนวดแผนไทย (Booking & Slot Validation)
ผู้กระทำ (Actor)ผู้ใช้บริการ (Customer)
วัตถุประสงค์เพื่อส่งคำขอจองคิวนวดแผนไทยในวันและเวลาที่ต้องการ
เงื่อนไขก่อนทำ (Pre-condition)ผู้ใช้เข้าสู่ระบบเรียบร้อยแล้ว และมีเบอร์โทรศัพท์ในระบบ
เงื่อนไขหลังทำ (Post-condition)ข้อมูลการจองถูกบันทึกลงใน Firestore, สร้างหมายเลขคิวประจำวัน และสถานะเป็น pending
ขั้นตอนหลัก (Main Flow) 1. ผู้ใช้เลือกแพ็กเกจบริการนวดแผนไทย (เช่น นวดเพื่อสุขภาพ, นวดประคบสมุนไพร)
2. ผู้ใช้เลือกวันที่รับบริการ (จองล่วงหน้าได้ไม่เกิน 3 วันตามเกณฑ์ศูนย์)
3. ผู้ใช้เลือกช่วงเวลา (Time Slot) และเลือกหมอนวดที่ต้องการ (ระบุหรือไม่ระบุก็ได้)
4. ผู้ใช้กดยืนยันการจองคิว
5. Backend ประมวลผลผ่าน Firestore Transaction ตรวจสอบว่าช่วงเวลาว่างอยู่หรือไม่
6. ระบบสร้างรหัสคิวใหม่ประจำวัน (เช่น A001, A002) และบันทึกข้อมูลการจอง
7. ระบบแสดงหน้ายืนยันการจองสำเร็จ พร้อมบัตรคิวอิเล็กทรอนิกส์
ขั้นตอนสำรอง (Alt Flow) 5a. ช่วงเวลาดังกล่าวถูกผู้อื่นจองไปแล้วในเสี้ยววินาทีเดียวกัน (Conflict 409): ระบบยกเลิก Transaction และแจ้งเตือน "เวลานี้ถูกจองแล้ว กรุณาเลือกช่วงเวลาอื่น"
ตารางที่ 3.3 รายละเอียด Use Case: UC-04 การติดตามสถานะคิวสด (Live Queue Tracking)
รหัส Use CaseUC-04
ชื่อกรณีการใช้งานการติดตามสถานะคิวสด (Live Queue Tracking)
ผู้กระทำ (Actor)ผู้ใช้บริการ (Customer)
วัตถุประสงค์เพื่อให้ผู้รับบริการทราบลำดับคิวปัจจุบันและประเมินเวลาในการเดินทางมารับบริการ
เงื่อนไขก่อนทำ (Pre-condition)ผู้ใช้มีรายการจองในวันปัจจุบันที่มีสถานะ pending หรือ confirmed
เงื่อนไขหลังทำ (Post-condition)แอปพลิเคชันแสดงหมายเลขคิวปัจจุบัน จำนวนคิวก่อนหน้า และเวลาคาดการณ์
ขั้นตอนหลัก (Main Flow) 1. ผู้ใช้เข้าสู่หน้า "คิวของฉัน" (Queue Screen)
2. แอปพลิเคชันส่ง Request GET /api/queue/my
3. ระบบคำนวณจำนวนคิวก่อนหน้า (Queues Ahead) และเวลาที่ต้องรอโดยประมาณ
4. แอปพลิเคชันแสดงผลหมายเลขคิวปัจจุบันที่กำลังรับบริการ และสถานะคิวของผู้ใช้แบบ Real-time
ขั้นตอนสำรอง (Alt Flow) 2a. ผู้ใช้ไม่มีคิวในวันปัจจุบัน: ระบบแสดงข้อความ "ไม่มีคิวที่กำลังรอรับบริการในวันนี้" พร้อมปุ่มแนะนำให้ไปหน้าจองคิว
ตารางที่ 3.4 รายละเอียด Use Case: UC-06 การรับแจ้งเตือนและกดยืนยันรับทราบ (Notification & Acknowledgement)
รหัส Use CaseUC-06
ชื่อกรณีการใช้งานการรับแจ้งเตือนและกดยืนยันรับทราบ (Notification & Acknowledgement)
ผู้กระทำ (Actor)ผู้ใช้บริการ (Customer), ผู้ดูแลระบบ (Admin)
วัตถุประสงค์เพื่อแจ้งเตือนเมื่อถึงคิว และให้ลูกค้ายืนยันรับทราบเพื่อลดภาระเจ้าหน้าที่ในการโทรติดตาม
เงื่อนไขก่อนทำ (Pre-condition)เจ้าหน้าที่มีการกดเรียกคิว หรือระบบมีการสร้าง Notification ให้แก่ผู้ใช้
เงื่อนไขหลังทำ (Post-condition)สถานะ Notification เปลี่ยนเป็น confirmed: true พร้อมบันทึกเวลาที่กดยืนยัน
ขั้นตอนหลัก (Main Flow) 1. เมื่อเจ้าหน้าที่เรียกคิว ระบบจะสร้างการแจ้งเตือน "ถึงคิวของคุณแล้ว"
2. แอปพลิเคชันของผู้ใช้แสดง Badge ตัวเลขแจ้งเตือนที่ไอคอนกระดิ่ง
3. ผู้ใช้เปิดหน้ารายการแจ้งเตือน และกดปุ่ม "รับทราบแล้ว"
4. ระบบส่ง Request ไปยัง POST /api/notifications/:id/confirm
5. สถานะในระบบแอดมินจะอัปเดตเป็น "ลูกค้ารับทราบแล้ว" เจ้าหน้าที่ไม่ต้องโทรติดตามซ้ำ
ขั้นตอนสำรอง (Alt Flow) 3a. ผู้ใช้ไม่กดยืนยัน: หน้าจอ Web Admin จะคงสถานะ "ยังไม่ยืนยัน" พร้อมแสดงเบอร์โทรศัพท์เพื่อให้เจ้าหน้าที่โทรติดต่อโดยตรง
ตารางที่ 3.5 รายละเอียด Use Case: UC-09 การจัดการคิวและเรียกคิวถัดไป (Queue Management & Call Next)
รหัส Use CaseUC-09
ชื่อกรณีการใช้งานการจัดการคิวและเรียกคิวถัดไป (Queue Management & Call Next)
ผู้กระทำ (Actor)ผู้ดูแลระบบ / เจ้าหน้าที่ (Admin / Staff)
วัตถุประสงค์เพื่อควบคุมลำดับการให้บริการ ปรับสถานะการจอง และเรียกคิวถัดไป

3.4 แผนภาพลำดับการทำงาน (Sequence Diagrams) พร้อมอธิบายหลักการทำงาน

แผนภาพลำดับการทำงาน (Sequence Diagram) แสดงปฏิสัมพันธ์และการแลกเปลี่ยนข้อความ (Messages) ระหว่างอ็อบเจกต์ในระบบตามลำดับเวลา เพื่ออธิบายกระบวนการทำงานหลักอย่างชัดเจน:

3.4.1 Sequence Diagram: กระบวนการยืนยันตัวตนผ่าน ThaiD Digital ID (OIDC Authentication)

แสดงขั้นตอนการเข้าสู่ระบบด้วยอัตลักษณ์ดิจิทัล ThaiD ซึ่งใช้มาตรฐาน OpenID Connect ร่วมกับกลไก PKCE (Proof Key for Code Exchange) และการตรวจสอบกุญแจสาธารณะ JWKS ดังแสดงในภาพที่ 3.2

ภาพที่ 3.2 Sequence Diagram แสดงกระบวนการเข้าสู่ระบบผ่าน ThaiD Digital ID

คำอธิบายหลักการทำงานของกระบวนการยืนยันตัวตน ThaiD:

  1. ผู้ใช้บริการกดปุ่ม "เข้าสู่ระบบด้วย ThaiD" บนแอปพลิเคชัน Flutter
  2. แอปพลิเคชันส่ง Request ไปยัง Express Backend ที่ Endpoint /api/auth/thaid
  3. Backend ทำ OIDC Discovery, สร้างรหัสลับ state ป้องกัน CSRF และสร้างคู่รหัส PKCE (code_verifier และ code_challenge ด้วยอัลกอริทึม SHA-256) จากนั้น Redirect ผู้ใช้ไปยังหน้ายืนยันตัวตนของ ThaiD DOPA
  4. ผู้ใช้ยืนยันตัวตนบนแอปพลิเคชัน ThaiD ในสมาร์ตโฟน
  5. ระบบ ThaiD ส่ง Authorization Code และ State กลับมายัง Callback Endpoint ของ Server
  6. Server ส่ง Authorization Code พร้อม code_verifier ไปแลกเปลี่ยน Token ผ่าน HTTP Basic Authentication
  7. ThaiD ส่ง ID Token (JWT) กลับมาให้ Server
  8. Server ตรวจสอบลายเซ็นของ ID Token ด้วยกุญแจสาธารณะ (JWKS) ของกรมการปกครอง ตรวจสอบความถูกต้องของเลขบัตรประชาชน (PID) และสร้าง Firebase Custom Token
  9. Server Redirect ผู้ใช้กลับมายังแอปพลิเคชัน Flutter พร้อมแนบ Token ใน URL
  10. แอปพลิเคชันนำ Custom Token ไปล็อกอินผ่าน Firebase Authentication เพื่อสร้าง Session การใช้งานที่สมบูรณ์

3.4.2 Sequence Diagram: กระบวนการจองคิวและการจัดการความพร้อมกัน (Concurrency Booking)

แสดงขั้นตอนการจองคิวซึ่งใช้เทคนิค Firestore Transaction เพื่อป้องกันไม่ให้เกิดการจองช่วงเวลาเดียวกันและหมอนวดคนเดียวกันซ้ำซ้อน (Double Booking Prevention) ดังแสดงในภาพที่ 3.3

ภาพที่ 3.3 Sequence Diagram แสดงกระบวนการจองคิวนวดแผนไทยแบบ Concurrency Transaction

คำอธิบายหลักการทำงานของกระบวนการจองคิว:

  1. ผู้ใช้บริการเลือกบริการนวด, วันที่, ช่วงเวลา และหมอนวดที่ต้องการ จากนั้นกดยืนยันการจอง
  2. แอปพลิเคชันส่ง Request POST /api/bookings พร้อมแนบ Firebase Bearer Token ใน Authorization Header
  3. Server เริ่มการทำงานแบบ Atomic ผ่าน db.runTransaction()
  4. ระบบทำการ Query ค้นหารายการจองในวัน เวลา และหมอนวดคนดังกล่าวที่มีสถานะ pending หรือ confirmed
  5. หากพบว่ามีการจองซ้ำซ้อน Transaction จะถูกยกเลิก (Rollback) ทันที และส่งรหัส Error 409 Conflict กลับไปยังแอปพลิเคชัน
  6. หากช่วงเวลาว่าง ระบบจะดึงค่าจาก Collection counters ประจำวัน เพื่อนำมาสร้างหมายเลขคิวลำดับถัดไป (เช่น A001, A002)
  7. ระบบเขียนเอกสารการจองใหม่ลงใน Collection bookings พร้อมบันทึกเวลา Server Timestamp
  8. เมื่อ Commit สำเร็จ Server จะส่งข้อมูลการจองพร้อมรหัสคิวกลับไปยังแอปพลิเคชันด้วยสถานะ 201 Created
  9. แอปพลิเคชันอัปเดต State ภายในและแสดงผลบัตรคิวให้ผู้รับบริการทราบทันที

3.4.3 Sequence Diagram: กระบวนการเรียกคิวและการแจ้งเตือนลูกค้ายืนยันรับทราบ

แสดงขั้นตอนเมื่อเจ้าหน้าที่กดเรียกคิว ระบบจะส่งสัญญาณแจ้งเตือนไปยังแอปพลิเคชันลูกค้า และรับการกดยืนยันรับทราบกลับมาที่แดชบอร์ด ดังแสดงในภาพที่ 3.4

ภาพที่ 3.4 Sequence Diagram แสดงกระบวนการเรียกคิวและกดยืนยันรับทราบการแจ้งเตือน

คำอธิบายหลักการทำงาน:

เมื่อเจ้าหน้าที่กดปุ่ม "เรียกคิวถัดไป" บน Web Admin ระบบจะส่งคำขอไปยัง Backend เพื่อค้นหาคิวที่รออยู่ตามลำดับเวลา และปรับสถานะเป็น in_service พร้อมทั้งอัปเดตเอกสาร queue_status ประจำวัน และสร้างข้อความแจ้งเตือนลง Collection notifications ฝั่งแอปพลิเคชันลูกค้าจะแสดง Badge แจ้งเตือน เมื่อลูกค้ากดปุ่ม "รับทราบแล้ว" ระบบจะส่งคำขอยืนยันกลับมาอัปเดต confirmed = true ทำให้เจ้าหน้าที่บน Web Admin ทราบทันทีว่าลูกค้ากำลังเดินเข้าห้องนวด โดยไม่ต้องโทรติดตามซ้ำ

3.5 แผนภาพความสัมพันธ์ของข้อมูล (Entity-Relationship Diagram: ER Diagram)

แผนภาพ ER Diagram แสดงโครงสร้างความสัมพันธ์ระหว่างเอนทิตี (Entities), คุณลักษณะ (Attributes), คีย์หลัก (Primary Keys), คีย์นอก (Foreign Keys) และความสัมพันธ์เชิงจำนวน (Cardinality) ของระบบจองคิวนวดแผนไทย ดังแสดงในภาพที่ 3.5

ภาพที่ 3.5 ผังแสดงความสัมพันธ์ของข้อมูล (Entity-Relationship Diagram: ER Diagram)

คำอธิบายหลักการทำงานและความสัมพันธ์ระหว่างเอนทิตี (Cardinality & Business Rules):

  • USERS กับ BOOKINGS (ความสัมพันธ์แบบ 1 ต่อ กลุ่ม - 1:N): ผู้ใช้บริการ 1 ท่าน (USERS) สามารถสร้างรายการจองคิวนวดแผนไทย (BOOKINGS) ได้หลายรายการในวันเวลาที่แตกต่างกัน โดยมี userId เป็น Foreign Key
  • SERVICES กับ BOOKINGS (ความสัมพันธ์แบบ 1 ต่อ กลุ่ม - 1:N): บริการนวดแผนไทยแต่ละแพ็กเกจ (SERVICES) สามารถถูกเลือกในรายการจองได้หลายครั้ง โดยมีการ Snapshot ชื่อและราคาไว้ใน BOOKINGS เพื่อป้องกันปัญหาข้อมูลเปลี่ยนย้อนหลัง
  • STAFF กับ BOOKINGS (ความสัมพันธ์แบบ 1 ต่อ กลุ่ม - 1:N): หมอนวดหรือแพทย์แผนไทย 1 ท่าน (STAFF) สามารถรับผิดชอบให้บริการการจองได้หลายคิวงาน (ในเวลาที่ไม่ซ้ำกัน) โดยมี staffId เป็น Foreign Key
  • BOOKINGS กับ NOTIFICATIONS (ความสัมพันธ์แบบ 1 ต่อ กลุ่ม - 1:N): การจองคิว 1 รายการ สามารถทำให้เกิดการแจ้งเตือนหลายครั้ง (เช่น แจ้งยืนยันการจอง, แจ้งเตือนเมื่อถึงคิว) โดยแต่ละแจ้งเตือนมีฟิลด์ confirmed เพื่อตรวจสอบว่าลูกค้ารับทราบแล้วหรือไม่

3.7 การออกแบบส่วนติดต่อผู้ใช้งาน (User Interface Architecture)

ส่วนต่อประสานผู้ใช้ได้รับการออกแบบตามหลัก Ergonomics UI และ Visual Hierarchy โดยแบ่งออกเป็น 2 ส่วนหลัก:

  • Flutter Client Application (สำหรับผู้ใช้บริการ): ใช้โทนสี Forest Green (#1B3A2D) และ Jade (#2E7D52) ร่วมกับตัวอักษร Noto Serif Thai และ Sarabun ประกอบด้วยหน้าจอหลัก ได้แก่ หน้าเข้าสู่ระบบ ThaiD/OTP, หน้ารายการบริการและขั้นตอนเลือกวันเวลา, หน้าบัตรคิวสด และศูนย์การแจ้งเตือน
  • Web Admin Dashboard (สำหรับเจ้าหน้าที่): พัฒนาในรูปแบบ Single Page Application (SPA) มี Sidebar นำทาง, การ์ดแสดงสถิติ Real-time, ตารางจัดการคิวพร้อมปุ่ม Call Next และปุ่มฟังก์ชันพิเศษ "Sync to Google Sheets" และ "Email หมอนวด" บนแถบ Topbar

3.8 สรุปผลบทที่ 3

บทที่ 3 ได้นำเสนอรายละเอียดการวิเคราะห์และออกแบบระบบจองคิวนวดแผนไทย ศูนย์สุขภาพชุมชนท่าวังหิน ครบถ้วนตามมาตรฐานวิศวกรรมซอฟต์แวร์ ทั้ง Use Case Diagram, Use Case Descriptions, Sequence Diagrams แสดงกระบวนการทำงานหลักพร้อมคำอธิบาย, ER Diagram แสดงความสัมพันธ์ของข้อมูล และรายละเอียดโครงสร้างฐานข้อมูล เพื่อเป็นพิมพ์เขียว (Blueprint) ที่สมบูรณ์สำหรับการพัฒนาระบบจริงในบทที่ 4 ต่อไป
